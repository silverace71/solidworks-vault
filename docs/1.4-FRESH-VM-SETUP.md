# Guide A — SWVAULT 1.4 fresh VM, private R2, direct multipart transfers

**Who:** SWVAULT administrator. **Platform:** new Ubuntu/Debian Linux VM (no old SWVAULT installed). **Destination:** `vault.lynxmotorsports.racing`.

This guide is for both (a) a completely new vault and (b) the **destination** VM for a one-time 1.2.9 migration. A 1.4.x -> later 1.4.x upgrade does **not** require a new VM. **Do not run these scripts on the original 1.2.9 production VM.**

## 1. Before you begin

- A separate, newly provisioned VM with outbound Internet access, Docker privileges, and adequate disk for the **entire historical vault** plus free space for temporary verification. Prefer a dedicated local backup/cold-storage disk. Do not size the VM only for the latest 100 GB workspace; historical Git LFS versions consume more space.
- Domain `lynxmotorsports.racing` active in your Cloudflare dashboard.
- A **private** R2 Standard bucket (e.g. `swvault-lfs`). Keep public bucket access and `r2.dev` **OFF**.
- R2 bucket-scoped **Object Read & Write** S3 credentials. Save the **Account ID**, **Access Key ID**, and **Secret Access Key** in your password manager. The Cloudflare account password is not required by SWVAULT.
- A dedicated Cloudflare **remotely managed tunnel** named `swvault-14`. Choose Docker as the connector and copy **only** the long `eyJ...` Tunnel token. Do not run the Cloudflare-provided Docker command; Compose starts cloudflared on the new VM.
- In the Tunnel, add a published application route: public hostname `vault.lynxmotorsports.racing`, service `HTTP`, origin `http://localhost:8080`. This localhost is **inside** the shared Docker network namespace, not your Windows PC. Do **not** create a public R2 route.
- A separate mounted backup disk destination (for example `/mnt/swvault-backups`). Keep backups independent of this VM and periodically test offline restores.

Cloudflare Tunnel and Gitea traffic consists of login, Git metadata, locks, signed URL requests, and small upload-control JSON. Large client files are sent as **32 MiB multipart PUTs directly to R2's S3 API endpoint**. The usual 100 MB Cloudflare proxied *upload* limit therefore does not apply to these part requests. A standard unmodified 1.2.9 client **does not** support this feature.

**Technical trade-off:** After a direct R2 upload, the new VM downloads the object **once** for SHA-256 validation and a local cold copy, then sends a canonical copy through Gitea's supported LFS PUT interface back to R2 so the Git LFS database is consistent. This means server bandwidth is *not zero* during check-in; client uploads and normal client downloads bypass the VM. The server-side finalization can take time, and Git commit happens **after** finalization. We intentionally avoided direct edits to Gitea's SQLite tables.

## 2. Stage the source on the new VM

Upload and extract `SWVAULT-1.4.0-GitHub-Source.zip` (or clone your GitHub repository). For a ZIP containing `SwVault-main`:

```bash
sudo apt-get update
sudo apt-get install -y unzip git
cd /tmp
unzip SWVAULT-1.4.0-GitHub-Source.zip
sudo mkdir -p /opt/swvault
sudo cp -a SwVault-main/. /opt/swvault/
cd /opt/swvault/server/linux
sudo chmod +x *.sh
sudo ./setup.sh
```

Setup asks **before deploying** for team name, organization, repository, admin user, Windows workspace path, SOLIDWORKS year, backup path, email policy, domain/hostname, Tunnel token, bucket, R2 Account ID, Access Key ID and secret. Credentials are entered on the VM, not in ChatGPT or GitHub. It validates R2 before bringing up the services. Setup requires typing `INSTALL` and `I_ACCEPT_PILOT_TESTING` on a fresh VM.

**If this VM will receive 1.2.9 data:** Match the original `ORG`, `REPO`, `ADMIN_USER` exactly. Use the same Windows `LocalRoot` to avoid remapping CAD references. The original server's `team.json` and `.env` contain these non-secret names. Do **not** run client registration against the blank destination repo. Continue with [Guide B](1.2.9-TO-1.4-MIGRATION.md).

## 3. Validate installation

```bash
cd /opt/swvault/server/linux
sudo ./swvault-admin.sh status
sudo docker compose ps
sudo docker compose logs --tail=75 cloudflared gitea r2-transfer proxy invites
curl -fsS https://vault.lynxmotorsports.racing/swvault-transfer/health
```

The health endpoint must say `direct_r2_uploads: true`. It checks the coordinator is running, **not** that Gitea registration works. A genuine 500 MB+ file check-in by a **1.4 Windows client** must be your acceptance test. For direct downloads, after at least one LFS object is committed:

```bash
sudo ./verify-r2-direct.sh
```

Do not treat a green container health check as approval to migrate production clients. Test check-in, check-out, new and historical versions, SHA-256, parallel requests, locks and a real backup restore.

## 4. Completely new vault: importing existing SOLIDWORKS files

For a clean new vault with no prior Git history, copy the CAD project directory to a **single** designated Windows import computer (not into a running user's synced folder). Install the 1.4 client from the built installer, sign in as the new admin, initialize the new vault once, then use the SWVAULT SOLIDWORKS add-in **Import Folder**. Preserve the original assembly directory structure and dependencies. Start with a small test assembly; then import the remainder in batches. Do not run simultaneous imports of the same files from multiple computers. Because Git LFS stores full changed file versions, imported data costs R2 storage even though egress is free.

If you are migrating an existing SWVAULT 1.2.9 vault, **do not import the CAD folder as new files**. That loses the existing repository's commit history and risks duplicate vault identities. Instead, migrate Gitea's original database, Git repositories, locks, and LFS objects using Guide B.

## 5. Cold backup, troubleshooting, and rollback

The `r2-transfer` service maintains `data/cold-lfs/` for new verified uploads. Imported old LFS objects remain in `data/gitea/git/lfs/` as cold copies. The nightly script separately backs up Gitea metadata, both local stores, and canonical private R2 objects. This requires an **independent** destination with enough capacity; a backup on the same VM disk is not a failure-independent copy.

Inspect logs (without posting secret values):

```bash
sudo docker compose logs --tail=100 r2-transfer
sudo ./swvault-admin.sh backup
sudo du -sh data/gitea/git/lfs data/cold-lfs
```

R2 staging uploads reside under the private `stage/` prefix. Configure an R2 lifecycle rule to abort incomplete multipart uploads; Cloudflare's default is generally seven days. Remove abandoned staged objects only after verifying they are not part of an active/failing finalization. Test restores routinely. To roll back a **new** vault, stop check-ins and restore the whole Gitea database/repository **and** corresponding LFS objects from the same recovery point; do not restore only `team.json`.

**Cloudflare docs:** https://developers.cloudflare.com/r2/objects/upload-objects/ and https://developers.cloudflare.com/r2/api/s3/presigned-urls/.
