# Guide B — One-time SWVAULT 1.2.9 (Tailscale) → SWVAULT 1.4 (new VM)

**This is the ONLY upgrade for which a fresh VM is required.** Existing users are on **1.2.9**, not 1.3. Keep the original server untouched during staging and the old client URL working until the final freeze. Never run 1.4 setup or the import script over the old production instance.

## Safety principles

- Preserve repository history, Git LFS metadata, file locks, user identities, old access tokens, invite/user settings, team configuration, and Windows working folders.
- **No split brain:** after the final 1.2.9 export, do not reopen the old server for check-ins. Otherwise files checked into the old vault will not exist on the new one. Every new write after the snapshot must go to 1.4.
- **No early client switch:** 1.4 clients carry both URLs, but only switch after the new server has accepted an imported Gitea database, passed a real multipart check-in/download pilot, and an admin runs `arm-129-cutover.sh`.
- **No silent repo recreation:** `ORG`, `REPO`, and `ADMIN_USER` **must match** exactly and the repository path must remain the same on both hostnames.
- The original 1.2.9 updater **offers** 1.4; it does not forcibly install it without a user's action. Send the installer manually to any members who miss the prompt.

## Stage 1: Record the ORIGINAL configuration and protect data

On the existing 1.2.9 VM:

```bash
cd /opt/swvault/server/linux
sudo ./swvault-admin.sh status
sudo du -sh data/gitea/git/lfs data/gitea
sudo cp -p .env /root/swvault-129-env.private.bak
sudo cp -p team.json /root/swvault-129-team.private.bak
```

Read (don't share passwords): `ORG`, `REPO`, `ADMIN_USER`, `TEAM_NAME`, `LOCAL_ROOT`, `SW_VERSION`, `VAULT_HOSTNAME`, `EMAIL_DOMAINS` and SMTP settings. Note your old repository URL from `team.json`, for example `https://<old-tailnet>.ts.net/fsae/cad.git`. Do NOT copy its Tailscale auth key to the new VM. Take an independent VM snapshot and a verified off-VM archive as well.

On the **fresh** 1.4 VM, follow [Guide A](1.4-FRESH-VM-SETUP.md). Choose the old organization's name, repo name and admin user. Set the Cloudflare URL to `vault.lynxmotorsports.racing` and your private R2 bucket. Never give this blank new vault to users yet.

## Stage 2: Package 1.4 and publish it through the OLD 1.2.9 update service

You can deploy the new 1.4 code and create a **pre-cutover** installer before the old vault is frozen. On a Windows build PC:

1. Copy `team.json` from the NEW VM. Add `"previousVaultUrl": "https://<old-tailnet>.ts.net/<org>/<repo>.git"`. Retain `"vaultUrl": "https://vault.lynxmotorsports.racing/<org>/<repo>.git"` and `"directR2Uploads": true`.
2. Build `1.4.0` (see [Guide C](1.4-WINDOWS-ROLLOUT.md)). Ensure your package contains the new `team.json` and both URLs.
3. Publish the **new client package** to the **old 1.2.9 update server**, not the empty new server:

```powershell
.\scripts\package.ps1 -Version 1.4.0 -TeamConfig .\team.json -Publish -PublishToPreviousVault -Required -Notes 'One-time SWVAULT 1.4 upgrade; keep using old vault until migration is enabled.'
```

The script asks for the **old** server's admin credentials and sends the installer ZIP there. The installer itself points to the new URL but **refuses to switch registrations** until the new VM exposes the admin-controlled readiness marker. Old users continue working on 1.2.9 or the upgraded 1.4 client against the old Tailscale URL during staging. The 1.4 agent checks the readiness marker at startup and every five minutes thereafter while idle.

**Important for people with uncommitted SOLIDWORKS edits:** Have them finish/check in outstanding changes, close SOLIDWORKS, accept the offered update, and confirm the installed version is 1.4.0. The new client will not erase local workspace data; it preserves the registered vault ID and folder. Have users back up unusual local uncommitted edits separately before the maintenance window.

## Stage 3: Final freeze/export of the original 1.2.9 VM

Choose a maintenance window after most users have installed the update. Copy **only** `server/linux/export-129-final.sh` from the 1.4 source ZIP to the ORIGINAL server's `server/linux/` directory (do NOT replace the original setup, Compose, auto-update or admin scripts). Run:

```bash
cd /opt/swvault/server/linux
sudo chmod +x export-129-final.sh
sudo ./export-129-final.sh /mnt/independent-backup/swvault-129-final.tar.gz
sha256sum -c /mnt/independent-backup/swvault-129-final.tar.gz.sha256
```

Type `FREEZE_129` only when users have stopped check-ins. This script stops original Gitea/invites, creates a private, checksum-listed, **complete offline snapshot** of Gitea, LFS, invites, admin token, environment and team configuration, and intentionally leaves old Gitea OFFLINE. It does **not** delete or modify original data. Store the archive encrypted/offline; it includes secrets, credentials and private CAD history. Do not upload it to GitHub or this chat.

If the export fails before you import to the new server, the script attempts to resume original services. If the migration is abandoned *before new clients write to 1.4*, you may restart original services manually with `sudo docker compose up -d gitea invites`.

## Stage 4: Import into the already configured, separate 1.4 VM

Copy that private archive onto the NEW VM and verify its SHA256 against the original VM's `.sha256` file. Run on the **NEW** VM:

```bash
cd /opt/swvault/server/linux
sudo ./import-129-fresh-vm.sh \
  /mnt/transfer/swvault-129-final.tar.gz \
  /mnt/independent-backup
```

The script requires `IMPORT_129` before replacing the **new VM's initial test DB**, backs up its initial clean state on an independent disk, and imports the original SQLite DB, Git repositories, LFS files, user accounts/tokens, invite metadata, email policy and Gitea encryption/JWT secrets. It migrates DB-referenced LFS content into private R2 using Gitea's native `migrate-storage` command. Old local LFS objects remain on the NEW VM for cold storage. It **does not arm** client switching. It does not modify the old VM.

If the Gitea storage migration fails, STOP. Do not arm the URL migration. Restore the new VM's saved pre-import archive or reattempt on another clean clone; do not repair it by creating a second repo with the same folder.

After importing, check:

```bash
sudo ./swvault-admin.sh status
sudo ./verify-r2-direct.sh
sudo docker compose logs --tail=100 gitea r2-transfer
```

Read `server/linux/team.json` to confirm it contains `previousVaultUrl`, `vaultUrl`, and `directR2Uploads: true`. Confirm that the former Git history and locks are present in Gitea, that existing users can authenticate, that historic file versions download from R2, and that `/swvault-transfer/migration-ready` is still 404 (switch OFF).

## Stage 5: Pilot on a real Windows client — REQUIRED

Choose one test workstation whose local files and unsaved CAD edits are backed up. Install the 1.4 EXE. Until the readiness marker is enabled, the client remains registered to the old URL. For a **new, isolated test profile** or admin pilot, enroll the NEW URL explicitly with a SEPARATE test workspace (not the existing production folder). Confirm:

- [ ] Login with an imported old account/token, and the original repository Git commit/history and LFS locks are visible.
- [ ] Check in a newly created 500 MB+ CAD-compatible test file. Capture Windows network activity: multipart part PUTs must go to `*.r2.cloudflarestorage.com`, **not** through your Tunnel/VM. No HTTP 413.
- [ ] Upload progress completes; the server finishes SHA-256 validation and Gitea registration **before** the Git commit is recorded. Monitor `docker compose logs r2-transfer` for errors.
- [ ] Download the file and a historic 1+ GB object directly via signed R2 GET; compare SHA-256 and verify history/locks.
- [ ] Confirm `/opt/swvault/server/linux/data/cold-lfs` contains a verified copy of the new test object. The old import's LFS data remains in `data/gitea/git/lfs`.
- [ ] Take a complete backup to an independent disk and test a restore in a sandbox.
- [ ] Simulate an interrupted upload; resending missing parts works within the active session. A process restart may need a new transfer session, but leaves local CAD data unchanged.

The multipart client, coordinator and Git LFS finalize integration have local tests, but they have **NOT** been live-tested against *your* R2 account/Gitea/Windows environment in this package. Do not infer pilot success from compilation or endpoint health alone.

## Stage 6: Arm the one-time URL cutover

After the old Gitea is frozen, complete the pilot, and audit last backups, run on the **new** VM:

```bash
cd /opt/swvault/server/linux
sudo ./arm-129-cutover.sh
```

This requires entering `PILOT_PASSED_AND_OLD_FROZEN`. It verifies the new Gitea branch and direct signed R2 download and writes `data/r2-transfer/migration-ready.json`. **Only then** do 1.4 clients switch from the old `*.ts.net` repository URL to `vault.lynxmotorsports.racing`, backing up their `vaults.json`, copying their saved credential, preserving vault ID and local workspace, and restarting the agent. Unsaved edits are not automatically discarded, but users should finish/check in before the server freeze.

One 1.4 agent may take up to about five minutes to switch while idle. A 1.2.9 agent cannot understand the migration marker and needs the EXE. **Do not decommission the old Tailscale host until you have checked every workstation**, then leave the old server powered off with an offline archive for the agreed retention period.

## Recovery / abort

**Before any new 1.4 check-ins:** Un-arm by removing the readiness marker on the new VM, stop new services, and restart original 1.2.9 Gitea/invites; clients already switched must be redirected back using their saved `.before-cloudflare-*.bak` registry backup and old credential. Do not blindly overwrite a client registry while SWVAULT is running.

**After any new 1.4 check-ins:** **Do NOT blindly revert the original 1.2.9 database.** It lacks new commits and objects. Freeze 1.4, take a fresh export, plan forward reconciliation/recovery, and verify every user's latest work before changing pointers. Keep the original backup immutable.
