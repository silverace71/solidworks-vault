# SWVAULT 1.4 — configuration, credentials, cold storage and backups

## GitHub-tracked source vs private runtime state

| Path | Contents | Publish to GitHub? |
|---|---|---|
| `server/linux/setup.sh`, `docker-compose.yml`, `Caddyfile.cloudflare`, `r2-transfer/` | Source and templates | Yes |
| `server/linux/.env` | Team/domain settings, R2 keys, Gitea encryption keys | **NO** |
| `server/linux/team.json` | Windows team settings, previous URL, optional invite code | Review/redact before publication |
| `server/linux/data/gitea` | Gitea SQLite, repos and legacy local LFS bytes | **NO** |
| `server/linux/data/invites` | Invites, people, installer update service state | **NO** |
| `server/linux/data/admin-token`, `data/cloudflare/tunnel-token` | Privileged server/tunnel bearer tokens | **NO** |
| `server/linux/data/r2-transfer/transfers.db` | Coordinator upload session metadata | **NO** |
| `server/linux/data/cold-lfs` | Verified local SHA-256 copies of newly uploaded files | **NO** |
| `server/linux/data/r2-rclone.conf` | R2 backup S3 credentials | **NO** |
| Private R2 `lfs/` | Full Git LFS history in canonical storage | Remote backup required |
| Private R2 `stage/` | Short-lived multipart upload staging | Cleanup, not version history |

For a **one-time 1.2.9 migration**, **do not copy old .env wholesale into the new VM**. Import only the historical Gitea encryption/JWT secrets, original organization/repository/admin names, invitation state, database and local Git/LFS history using `import-129-fresh-vm.sh`. Keep the new Cloudflare token, R2 API keys, new public hostname, and new backup destination from fresh `setup.sh`.

```bash
# On NEW VM, once installed:
cd /opt/swvault/server/linux
sudo ./swvault-admin.sh backup
sudo ./swvault-admin.sh status
sudo du -sh data/gitea/git/lfs data/cold-lfs
```

Your independent backup must contain **Gitea SQLite and Git repos, invites, old local LFS objects, newly verified cold LFS objects, and R2 canonical objects**. A current workspace directory alone is not a complete Git LFS history backup. Restore-test on an offline clone; make sure the Gitea DB and R2 object snapshot are consistent.

The upload coordinator currently writes cold content to `server/linux/data/cold-lfs`, which should be **on a sufficiently sized independent storage volume** in a hardened production environment; the fresh Compose bind mount defaults to VM data for simplicity. Mount your cold disk at that path before production and keep a second, offline backup elsewhere. The nightly backup is a backup copy, not a replacement for immutable snapshots.

On Windows, a one-time migration backs up `vaults.json` alongside itself (timestamped `before-cloudflare` suffix), retains `Id` and `LocalRoot`, copies the old Gitea credential to the new HTTPS hostname in Windows Credential Manager, and changes the Git mirror remote on the next Agent start. The user's actual CAD workspace is not copied or deleted. Stop the Agent/SOLIDWORKS before manually restoring a registry backup. Once new writes occur on 1.4, rolling back to the old 1.2.9 server without reconciling Git commits is unsafe.

Never put the R2 secret, Tunnel token, old VM export tarball, `vaults.json` or private installer packages in a GitHub commit. Use private/offline backup storage with access controls and encryption.
