# Guide C — Build the SOLIDWORKS plugin and update 1.2.9 users to 1.4

Existing users are on **SWVAULT 1.2.9**. There is **no intermediate 1.3 installation**. The 1.4 package must be published to the ORIGINAL Tailscale service and installed BEFORE its final export for the smoothest rollout.

## 1. Prerequisites on your Windows build PC

- Windows 10/11 x64 with **.NET SDK 10** installed: `winget install Microsoft.DotNet.SDK.10` (verify `dotnet --info`).
- **Inno Setup 6**: `winget install JRSoftware.InnoSetup` (or download from the vendor). This produces the Windows Setup EXE; without it, the build can still produce a ZIP.
- A test installation of SOLIDWORKS with a compatible API version for integration testing. The repo includes SOLIDWORKS interop DLLs but cannot actually exercise a running SOLIDWORKS process in CI.
- Git for Windows (optional for development; packaging downloads and bundles MinGit by default).
- The new VM's `team.json` copied into a local checkout (NOT committed to GitHub if it includes organization-specific settings you prefer private). Ensure `previousVaultUrl` is the ORIGINAL repository URL and `directR2Uploads` is true.

This version can be built locally or with the included GitHub Actions workflow. Never commit `.env`, Gitea SQLite, R2 keys, Tunnel tokens or private exports to GitHub.

## 2. Prepare the client migration configuration

Your `team.json` must look like the following (adjust `org`, `repo`, old host, Windows root to your actual old settings):

```json
{
  "name": "FSAE",
  "vaultUrl": "https://vault.lynxmotorsports.racing/fsae/cad.git",
  "previousVaultUrl": "https://YOUR-OLD-TAILSCALE.ts.net/fsae/cad.git",
  "directR2Uploads": true,
  "localRoot": "C:\\SWVault\\FSAE",
  "admin": "YOUR_ORIGINAL_ADMIN_USER",
  "downloadAllOnJoin": true
}
```

**Critical:** Keep the exact existing organization/repository path and `localRoot`. The client intentionally checks that the path didn't change; it preserves the old vault's ID and workspace rather than creating duplicate vault entries. Do not add new registrations pointing at the same CAD working directory manually.

## 3. Build and test locally

From the new 1.4 source checkout in PowerShell:

```powershell
Get-Content .\version.txt
# Expected: 1.4

dotnet restore .\SwVault.slnx
dotnet test .\SwVault.slnx -c Release

.\scripts\package.ps1 -Version 1.4.0 -TeamConfig .\team.json
```

Look in `dist/` for `SwVault-<Team>-1.4.0.zip` and `SwVault-<Team>-1.4.0-Setup.exe`. Use the EXE on one disposable Windows pilot client first. Confirm the add-in loads in SOLIDWORKS and the tray shows SWVAULT 1.4.0. Do a 500 MB+ R2 upload/download on the new VM using a **separate pilot workspace**, followed by ordinary check-in/out, locking and Git history tests.

### GitHub Actions build

1. Upload this source ZIP's **contents** to a new private GitHub repository; do not upload the ZIP as a GitHub release source attachment and assume builds happen automatically.
2. Go to **Settings → Secrets and variables → Actions → Variables**. Define `TEAM_JSON` as the JSON above. For a public repository, consider placing team settings in a private repo, and do not include any secrets in the JSON. Optional: `TEAM_ICON_PNG_B64`.
3. Go to **Actions → Nightly release → Run workflow**. The Windows job runs tests, builds the agent, SOLIDWORKS add-in, package ZIP and Setup EXE, and uploads build artifacts. Verify it completes; this package has not been locally compiled with a Windows SDK.
4. Download the workflow's installer artifacts. Code/build success does not substitute for testing inside the target SOLIDWORKS version.

## 4. Publish the 1.4 client through the OLD 1.2.9 server

While the OLD server is still accepting logins/downloads:

```powershell
.\scripts\package.ps1 `
  -Version 1.4.0 `
  -TeamConfig .\team.json `
  -Publish `
  -PublishToPreviousVault `
  -Required `
  -Notes 'One-time migration to SWVAULT 1.4. Close SOLIDWORKS, install this update, and keep using the old vault until cutover.'
```

The key switch is **`-PublishToPreviousVault`**: it sends this installer to the original Tailscale 1.2.9 update endpoint even though the packaged `team.json` points to the new Cloudflare URL. It prompts for the old admin login; the credentials are never included in the release ZIP. Run this BEFORE freezing the old server.

Members receive the existing 1.2.9 update notification (the ordinary check runs on a schedule, or via tray icon → Check for updates). **The 1.2.9 updater does not silently force-install releases**. Each user must accept the update or run the EXE you distribute. SOLIDWORKS must be closed for installation.

## 5. How automatic URL migration actually works

After 1.4 installs:

1. The new client sees its saved 1.2.9 registration, including original vault ID, local CAD folder, and saved Gitea access token.
2. If the new VM has **not** been armed, the client continues using the old Tailscale URL. It checks again every five minutes while idle.
3. After a final old-server snapshot is imported and a 500MB+ pilot succeeds, the administrator runs `arm-129-cutover.sh` on the new VM.
4. The 1.4 client checks the marker's `source` and `target` against its packaged `team.json`, validates its existing token against the imported Gitea DB on the new VM, saves a timestamped registry backup, and changes only the saved remote URL. It copies (not destroys) its old saved credential, retains the vault ID and local root, and restarts the agent to reload Git connections.
5. Files are **not** blindly reimported or deleted. Because the original Gitea history was imported, `Get Latest` can fetch just changed objects from R2. If a client's old token fails, migration is skipped; an admin must investigate/re-authenticate, and the client retains the previous registration.

For safety, do not arm during an active team check-in window. Finish pending jobs, close SOLIDWORKS and make a local copy of important uncommitted edits first.

## 6. Track all workstations before retiring Tailscale

Maintain a spreadsheet of usernames/computers and confirm each one has: installed 1.4.0, updated vault URL, original local root, original vault ID, complete current branch, locks correct, and a successful 100MB+ R2 upload test for at least one pilot account. The installer can be manually sent to offline users. This release does not provide a server-side proof that every PC updated; do not assume a `Required` update means universal installation.

**Rollback:** Every migrated Windows registration has a `vaults.json.before-cloudflare-<timestamp>.bak` file under `%LOCALAPPDATA%\SwVault` (or profile-specific folder). Restore it only after stopping the agent and coordinating server state. After new commits, restoring the old 1.2.9 endpoint without reconciling Git history is not safe.
