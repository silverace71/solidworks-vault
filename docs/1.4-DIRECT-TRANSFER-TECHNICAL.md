# SWVAULT 1.4 — actual file-transfer protocol

**This is an implemented pilot transfer path, not a claim of completed live interoperability testing.**

1. Client performs the Gitea LFS `objects/batch` upload request and only uploads missing objects.
2. For objects >= 8 MiB and a team config with `directR2Uploads: true` matching the server URL, the client issues `POST /swvault-transfer/init` with `{oid,size}` and its normal Gitea Basic token. Small objects use ordinary Gitea LFS upload (<100 MB).
3. Coordinator validates `/api/v1/user` and repository push rights on *every* request, creates an unguessable R2 staging key and multipart session, and records it in SQLite.
4. Client requests a short-lived presigned `upload_part` URL for each 32 MiB part. It verifies the URL is `https://<account>.r2.cloudflarestorage.com`, and uploads up to four parts in parallel per file directly to R2. It never sends permanent R2 API keys or its Gitea token to R2. Failed parts are retried with new URLs.
5. Client issues `POST /swvault-transfer/complete`; coordinator lists and validates part count/sizes, completes R2 multipart upload asynchronously, downloads a cold copy to local disk, validates exact length and SHA-256, calls Gitea's native `PUT /<org>/<repo>.git/info/lfs/objects/<oid>/<size>`, and verifies the LFS `objects/batch` download action is a signed R2 GET. It removes the temporary stage object on success.
6. Client polls `/swvault-transfer/status` until `done`, and only then proceeds to its normal Git commit/push. If verification/registration fails, the check-in fails without committing a missing object.
7. Gitea canonical storage is private R2 `lfs/`; the VM retains cold copies and the backup service copies R2 and metadata independently. Clients perform large GETs directly from R2 signed URLs.

**Bandwidth truth:** Workstation-to-VM payload traffic is avoided for these large uploads/downloads. During check-in, however, the VM must pull the staged object once (cold copy/hash) and push it once into canonical R2 through Gitea's supported LFS API. This is an interim correctness-first design; removing the canonical re-upload would require a rigorously tested, atomic Gitea-compatible metadata registration interface, preferably as an upstream-supported Gitea extension.

**Limits:** Cloudflare's 100 MB proxied-upload cap applies to Tunnel requests, not to `*.r2.cloudflarestorage.com` S3 multipart UploadPart requests. 32 MiB parts fit the S3 multipart range (5 MiB minimum except last). SWVAULT/Gitea sets a 4 GiB per-file maximum by default. Increase only after testing staging disk, SHA256, Gitea file-size and workload requirements.

**Security/ops:** Each part URL is a bearer authorization with a short expiry. Private bucket, least-privilege R2 keys, HTTPS, authenticated per-repo coordinator endpoints, digest verification, short-lived URLs, 24-hour session window, and two concurrent finalizers reduce risk but do not eliminate operational threats. Use VM firewall, independent backups, monitoring, R2 lifecycle cleanup, and periodically test full restores. The coordinator is not compatible with plain Git LFS clients that do not implement SWVAULT's custom multipart control API.

**Pilot acceptance:** 8 MiB, 99 MiB, 500 MiB, and 1+ GiB check-in; two parallel check-ins; retry of a failed part; corrupt-hash rejection; Gitea lock/permission denial; historical file GET; real Windows SOLIDWORKS add-in check-in; backup restore. Never arm the 1.2.9 migration based only on a health endpoint.
